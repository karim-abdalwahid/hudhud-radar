## 9️⃣ سؤال المالك (موثق بالدليل التجريبي): "أنا كإنسان أشوف يوزر المُراسل — ليه الـ API لا يجيبه؟"
- **الاختبار الحي على PSID حقيقي (Graph v21.0)**:
  - `first_name,last_name,profile_pic` → **OK** (ما نلتقطه حاليًا = الحد الأقصى الرسمي).
  - `username` → **FAIL**: خطأ ميتا الصريح "username field is deprecated for versions v2.0 and higher" — أي أن ميتا منعت الـ username من الـ API منذ 2014 (v2.0) عمدًا.
  - `link` → يرجع الـ id فقط بلا رابط. `email/phone` → FAIL (حقول غير موجودة أصلًا في هذا السياق).
- **الخلاصة المعتمدة**: "مرئي للإنسان" ≠ "متاح للـ API" — ميتا تفصل الاثنين بتصميمها. الحل البديل الوحيد (كشط facebook.com) مخالفة صريحة لشروط ميتا (Automated Data Collection Terms) + خطر مباشر على App Review والتطبيق كله، ويخالف مبدأ المشروع الثابت (الكشط عبر القنوات الرسمية فقط).
- **مقارنة صناعية**: ManyChat/Chatfuel وأمثالهم يحصلون على نفس الحقول الثلاثة بالضبط لمراسلي ماسنجر.
- **تبعات سؤال المالك عن الـ ID ("رجّع ID — نبني بيه رابط؟")**: الـ ID الراجع لمراسلي ماسنجر = **PSID (Page-Scoped ID)** — معرّف ميتا المخصص لكل صفحة، وليس الـ Global ID الحقيقي للبروفايل؛ نفس الشخص يأخذ PSID مختلفًا لكل صفحة (تصميم منع التتبع v2.0). لذلك `facebook.com/{PSID}` لا يفتح البروفايل — والـ PSID يظل المفتاح التشغيلي المشروعي (إرسال، مطابقة حتمية، rate limits، وبصلاحية Business Asset User Profile Access: المطابقة الرسمية عبر قنوات المالك نفسها). ملاحظة نزاهة مفتوحة: `extract_from_facebook` يبني `profile_url = facebook.com/{id}` لما لا يوجد link — لمراسلي ماسنجر هذا رابط لا يعمل (مرشح للتنظيف ضمن Zero-Fabrication).
- **المكمل المشروعي**: بيانات التواصل (email/phone) تُلتقط تلقائيًا من نص المحادثة عند ورودها (`extract_contact_info` — منفذ في مسار الرسائل) وتظهر في الـ Dossier فورًا.
